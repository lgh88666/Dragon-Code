# LLM Client 术语统一 Spec

## 背景

Dragon Code 在 ch02 中为 Anthropic 与 OpenAI 两种协议建立了统一适配层，目前代码将这层抽象称为“Provider”。

Code Agent 教材的 Python 源码把同一职责称为“LLM Client”：上层只依赖统一客户端接口，不感知具体 API 协议；不同协议客户端负责请求格式转换、流式事件解析与错误映射。

当前命名虽然功能正确，但不利于源码对照学习，也容易把“模型服务商配置”与“LLM API 客户端”混成同一个概念。

## 目标

- Dragon Code 的代码抽象统一采用教材中的“LLM Client”术语。
- Anthropic 与 OpenAI 的具体实现统一称为对应协议的 Client。
- 错误类型、创建入口、模块目录和代码注释同步使用客户端术语。
- YAML 中的 `providers:`、服务商配置模型和 TUI 的 Provider 选择语义保持不变。
- 本次只修改命名和代码组织，不改变请求、流式解析、Agent Loop、工具调用或 TUI 行为。
- 修改后现有配置文件无需调整，已有功能与测试行为保持一致。

## 功能需求

- F1：统一客户端抽象。所有负责调用 LLM API、发送请求、接收流式响应的代码统一使用“LLM Client”术语，不再以“Provider”命名这层代码抽象。
- F2：统一协议客户端。Anthropic 与 OpenAI 两个协议实现继续遵循同一个客户端接口，对 Agent 暴露一致的异步流式事件；本次改名不改变任何协议行为。
- F3：统一关联命名。客户端创建入口、客户端异常、模块注释、类型标注、测试名称和导入路径同步调整，不保留旧代码名称或兼容别名。
- F4：保留服务商配置术语。YAML 的 `providers:`、服务商配置列表、启动时的 Provider 选择界面保持不变。这里的 Provider 表示用户配置的模型服务商，不是代码客户端抽象。
- F5：调用方完整迁移。Agent、流式收集器、TUI、测试和公共导出全部改用新的客户端接口，不得继续依赖旧模块路径或旧类型名称。
- F6：运行行为不变。Anthropic/OpenAI 请求构造、流式文本、工具调用、错误恢复、多轮 Agent Loop、Token 统计及界面行为与改名前保持一致。

## 非功能需求

- N1：可读性。命名尽量直接，与教材 Python 源码中的概念保持一致；保留必要的中文注释，不引入复杂兼容层或高级抽象。
- N2：配置兼容。现有 `.dragon-code/config.yaml` 无需修改即可继续启动，密钥、模型和协议配置保持原样。
- N3：行为兼容。本次重构不得改变网络请求内容、事件顺序、异常恢复或用户可见交互。
- N4：迁移完整。源码和测试中不得残留旧客户端抽象的导入路径、类名或工厂名称；表示“服务商”的 Provider 用法除外。
- N5：质量检查。全部现有测试通过，格式化与静态检查通过；重命名后的两种协议客户端均有真实调用方和对应测试覆盖。
- N6：密钥安全。重构过程中不得在测试输出、异常、注释或日志中暴露真实 API Key。

## 不做的事

- 不修改 YAML 中的 `providers:` 字段，也不迁移用户现有配置。
- 不重命名表示“模型服务商配置”的概念，例如 Provider 选择界面与服务商列表。
- 不改变 Anthropic、OpenAI 或 DeepSeek 兼容端点的请求格式。
- 不新增缓存、System Prompt、System Reminder 或 ch05 的其他功能。
- 不修改 Agent Loop、工具系统、权限策略或 TUI 布局。
- 不保留旧客户端类名、旧模块路径或兼容别名。
- 不借重命名顺便重构业务逻辑、拆分复杂模块或加入新的抽象层。
- 不修改用户当前尚未正式纳入 Spec 的 `/help` 功能行为。

## 验收标准

- AC1（F1/F3/F5）：源码与测试中的 LLM 通信抽象统一使用“LLM Client”术语；搜索确认旧客户端类名、工厂名和旧导入路径均已清除。
- AC2（F2/F6）：Anthropic 与 OpenAI 客户端分别运行原有流式解析测试，文本、工具调用、用量和错误事件结果与改名前一致。
- AC3（F4/N2）：使用现有包含 `providers:` 的配置文件启动 Dragon Code，无需修改配置即可进入原有 Provider 选择或对话界面。
- AC4（F5/F6）：Agent Loop 仍能通过统一客户端完成“模型请求 → 工具调用 → 结果回灌 → 最终答复”的完整流程。
- AC5（F4）：TUI 仍以 Provider 表示用户选择的模型服务商，状态栏中的服务商名称和模型名称显示正常。
- AC6（N3）：重构前已有的全部自动化测试继续通过，没有因改名产生行为差异。
- AC7（N4）：代码搜索中只允许在配置、服务商选择和用户可见服务商语义中出现 Provider；客户端抽象中不得残留。
- AC8（N5）：`ruff check .`、`ruff format --check .` 和 `pytest` 全部通过。
- AC9（端到端）：在 tmux 中启动 Dragon Code，发送一条需要模型回复的真实请求，能正常流式回复；再发送一条需要工具的请求，Agent Loop 正常执行。
- AC10（N6）：测试、启动输出和异常信息中不出现真实 API Key。
